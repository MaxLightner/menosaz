# انتقال مرحله‌ای به مدل واحد

این سند عملیات اجرایی نیست. تا export مدیریتی و بررسی schema واقعی انجام نشود هیچ migration زنده‌ای اجرا نمی‌شود. موفقیت `/health` یا خواندن منوی عمومی، تطبیق کامل schema را ثابت نمی‌کند.

## ۱. پیش‌نیاز قبل از اولین تغییر

1. ثبت commit فرانت و کد دقیق Edge منتشرشده، نام و نسخه تابع‌های SQL، constraintها و grantها؛ تطبیق با migrationهای مخزن.
2. پشتیبان خصوصی رمزگذاری‌شده از schema و داده public، هویت‌ها/نقش‌های لازم Auth با حفظ UID و manifest رسانه‌های Storage. روش بازیابی کاربران و نشست‌های Auth مطابق دسترسی واقعی بررسی شود؛ export دستی ناقص جای پشتیبان کامل را نگیرد.
3. پشتیبان فایل‌های لازم Storage با checksum و تعداد؛ URL فایل به‌تنهایی پشتیبان فایل نیست.
4. آزمون بازیابی در محیط جدا؛ ثبت شمار رکورد، مجموع مبالغ و ارتباط حساب‌ها. کلیدها، dump و توکن‌ها وارد GitHub نمی‌شوند.
5. inventory فقط‌خواندنی همه مجموعه‌ها؛ داده عمومی پیچ شمرون نماینده تمام حساب‌ها نیست.
6. گزارش داده مبهم/ناسازگار و تصمیم صریح نگهداری؛ پاک‌کردن یا تولید خودکار داده واقعی مجاز نیست.

## ۳. سفارش‌ها و نشست‌های تاریخی

- سفارش تحویل‌شده/لغوشده: نشست تاریخی بسته با source=legacy_import؛ سفارش‌های یک میز صرفاً به‌خاطر شماره میز به یک نشست فعال تبدیل نشوند.
- سفارش باز: پیش از انتقال شمارش و با مسئول مجموعه تطبیق داده شود. حالت ترجیحی cutover وقتی سفارش باز نیست؛ در غیر این صورت انتقال دستی نشست فعال لازم است، نه حدس از تاریخ.
- guestTokenHash سفارش‌های فعلی برای پیگیری همان سفارش حفظ و از endpoint قدیمی اعتبارسنجی می‌شود؛ این توکن حق دیدن سفارش‌های دیگر نشست را پیدا نمی‌کند. مسیر legacy-status موقت فقط خواندنی است و از جداول جدید می‌خواند.
- status=cooking فعلی فقط به معنی ارسال‌شده است؛ restaurantConfirmed=true تأیید قبلی را نشان می‌دهد. رویداد دریافت/آماده‌شدن که قبلاً وجود نداشته با زمان جعلی ساخته نمی‌شود؛ وضعیت واردشده و منشأ legacy ثبت می‌شود.
- paid_cash/pos/online فعلی به entry افتتاحیه با source=legacy تبدیل می‌شود؛ سند دریافت جدید یا تراکنش بانکی تازه ایجاد نمی‌شود. تناقض unpaid+delivered گزارش توقف است.
- delivered_quantity برای اقلام تحویل‌شده از وضعیت معتبر قبلی پر می‌شود. آماده‌بودن مستقل اقلام تاریخی که معلوم نیست جعل نمی‌شود.
- شماره سفارش‌های موجود حفظ؛ شمارنده تازه از بیشینه معتبر شروع شود. شناسه و کلید تکراری بررسی شود.
- محصول حذف‌شده سفارش تاریخی، product_id=null و snapshot دست‌نخورده دارد؛ برای رفع FK محصول ساختگی ایجاد نمی‌شود.

## ۴. برش‌های اجرا؛ فقط یک نویسنده در هر بخش

| بسته | تغییر منبع حقیقت | حفظ رابط و مرز قطع |
|---|---|---|
| ۲ | business/menu/category/product از JSON به جدول | facade برای شکل پاسخ فعلی؛ نوشتن catalog در payload متوقف و کلیدهای منتقل‌شده از payload فعال خارج می‌شوند |
| ۳ | ویزارد/نمونه و رسانه و ظاهر به سرویس catalog واحد | atomic create، سقف از entitlement، Firebase upload حذف؛ تغییر ظاهر مرجع دوم ندارد |
| ۴ | حساب و عضویت و نقش به مدل access | Auth UID حفظ؛ endpointهای فعلی خروجی account سازگار می‌دهند؛ تخصیص مدیر از روی شماره حذف |
| ۵ | نقطه، QR، نگاشت منو و زمان‌بندی | لینک‌های چاپ‌شده قبلی business+table را resolve و menu قدیمی را نادیده می‌گیرند؛ انتخاب مجاز از سرور |
| ۶ | session/order/item/payment-entry به مدل سفارش | catalog فقط جدید است؛ نوشتن orders/calls در payload متوقف؛ کلید تکرار و guest grant قدیمی کنترل می‌شود |
| ۷–۸ | فرمان نقش‌محور و اعلان/خدمات/پیگیری | facade قدیمی فقط تا اتصال همه سه نما؛ حذف منطق مستقل frontend/SQLite |
| ۹ | اشتراک و پرداخت و محتوای پلتفرم | اطلاعات مالی و اعتبار قبلی حفظ؛ callback فقط GitHub؛ منبع محتوای سایت از مجموعه نمونه جدا |
| ۱۰ | حذف کد و storage قدیمی و facadeهای مصرف‌شده | schema legacy از مسیر runtime خارج؛ نسخه پشتیبان خصوصی برای بازیابی باقی می‌ماند |

در طول مراحل، JSON باقیمانده فقط داده هنوز منتقل‌نشده را نگه می‌دارد؛ هیچ موجودیتی هم‌زمان دو منبع معتبر ندارد. نگهداری archive پشتیبان دیتابیس عملیاتی دوم نیست. به‌روزرسانی catalog هنگام وجود سفارش باز باید قواعد ثابت قدیمی یا توقف کوتاه نوشتن داشته باشد؛ پاسخ اشتباه یا نیمه‌منتقل‌شده قابل انتشار نیست.

بین بسته ۲ و ۶، ثبت سفارش فعلی هنوز می‌تواند به فضای سفارش legacy بنویسد، ولی برای قیمت/گزینه و خواندن محصول فقط از catalog جدید استفاده می‌کند؛ نباید برای سازگاری، کپی محصول را در payload نگه دارد. facade واسط این اتصال را انجام می‌دهد و همراه انتقال سفارش حذف می‌شود. callback و API مالی نیز تا انتقال بسته ۹ فقط یک نویسنده فعلی دارند.

## ۵. عملیات انتقال هر برش

1. schema افزایشی در محیط جدا؛ import تکرارپذیر با کلید business+legacy_id و دفتر mapping.
2. dry-run با گزارش شمار، FK، مبلغ و هش داده‌های snapshot؛ بدون تماس با OTPy یا درگاه پرداخت.
3. تطبیق رفتار facade و API جدید با رابط موجود؛ آزمون مجوز دو مجموعه و دو نقش واقعی.
4. توقف کوتاه نوشتن همان دامنه، snapshot نهایی و catch-up از آخرین version؛ جلوی تراکنش در حال نوشتن هم گرفته شود.
5. انتقال نهایی، بررسی و تغییر نویسنده به مدل تازه. rollback readiness قبل از بازکردن نوشتن تأیید شود.
6. Edge سازگار با قرارداد قدیم/جدید منتشر، سپس فرانت GitHub. قرارداد/نسخه داده در health/bootstrap اعلام شود؛ mismatch بی‌صدا به نمونه برنگردد.
7. بازکردن نوشتن و بررسی مسیر واقعی؛ ثبت deployment، revision و نتیجه در handoff همان بسته.

پشتیبانی کوتاه از فرانت cache‌شده با همان نویسنده جدید انجام می‌شود. بازه سازگاری یک چرخه انتشار پایدار است؛ درخواست نوشتن از نسخه قدیمی ناسازگار خطای UPDATE_REQUIRED دارد، نه ذخیره با منطق منسوخ.

## ۶. کنترل صحت و معیار توقف

- شمار کسب‌وکار، منو، دسته، محصول، نقطه و سفارش؛ اختلاف صفر مگر گزارش تأییدشده.
- مجموع سفارش، قلم، دریافت و پرداخت اشتراک با واحد پول مشخص؛ اختلاف صفر.
- هیچ FK بدون مالک، نقش ناخواسته یا داده مجموعه دیگر وجود نداشته باشد.
- ثبت هم‌زمان سفارش دوبار نتیجه مالی یا سفارش دوم نسازد؛ بدنه متفاوت با همان key رد شود.
- منوی شبانه و ساعت پایان، نقطه selected/all و QR چاپ‌شده قبلی کنترل شوند.
- ویزارد یا کپی نمونه شکست‌خورده صفر خروجی نیمه‌ساخته بگذارد.
- آشپزخانه مبلغ نگیرد؛ گارسون تیک آشپزخانه نزند؛ مهمان سفارش مهمان دیگر را نخواند.
- قوانین باعث ارسال OTP یا logout نشود؛ کاربر تکراری Auth ایجاد نشود.
- هر اختلاف مالی، مالکیت نامعلوم، شکست بازیابی یا عدم تطبیق schema باعث توقف همان cutover است.

## ۷. بازگشت

پیش از بازکردن نوشتن تازه: endpointها و فرانت به commit/تابع پشتیبان برگردند و snapshot کنترل‌شده بازیابی شود.

پس از ثبت داده تازه: بازگرداندن dump قبلی مجاز نیست، چون سفارش و پرداخت تازه را پاک می‌کند. ابتدا نوشتن متوقف، داده تازه export و تطبیق داده می‌شود؛ سپس forward-fix یا تبدیل معکوس آزموده‌شده اجرا می‌شود. تا وقتی تبدیل معکوس وجود ندارد، راه امن forward-fix روی جداول جدید است. فرانت سازگار قبلی می‌تواند روی facade جدید برگردد، بدون بازگرداندن منبع داده.

گزارش هر انتقال شامل منبع/مقصد، تعداد، مجموع پول، exceptions، commit، نسخه Edge و نتیجه کنترل دسترسی است. نگهداری dump و اطلاعات کاربران خارج از GitHub و طبق دسترسی محدود انجام می‌شود.
